# 多 Agent 真实试用与人工评分记录

对应 M19（真实小规模验收）与 M20（按人工反馈校准）。当前没有真实试用数据，本文是待填写模板，不是质量提升结论。离线流程和报告验证见 [项目档案](project-change-log.md)。

## M19：先跑一组小样本

1. 用自己的小红书 PC 账号搜索 20 篇，记录关键词、排序和时间条件。勾选后采集；有效正文至少 3 篇，实际数量据实填写。
2. 选择自己的文字模型，先生成 **1 个标题 × 2 版文案**，记录模型、受众、创作要求和任务编号。不要在记录里填写 Cookie、API Key 或含凭证的服务地址。
3. 页面查看各阶段和请求计数；下载 HTML/JSON；切换文案、复制正文及完整笔记，确认正文和配图配套。
4. 由实际写稿/配图的同事先看成稿并评分，再展开模型评审，避免模型高分影响人工判断。说明具体哪句话/哪个画面不可用，而非只写“不够爆款”。
5. 超时或失败时记录错误类型、失败阶段、实际请求数；先核对中转站记录。网络超时不自动重试，不以反复生成充当质量验收。

新任务默认多 Agent，一次全部通过通常需要 10 次模型请求；返工可能增加请求，受 36 次/每阶段两次质量返工的上限约束。真实操作会使用自己的平台与模型服务，可能产生费用。

## M20：按真实反馈校准

需要对照时，在同一采集任务中保持同一模型、受众、要求、标题和版本数量，通过高级生成选项切换“旧版一次综合生成”，再用已采集正文生成；这会另行调用模型。保留新旧任务编号和两份报告，不重新搜索替换样本。将两组稿件标成 A/B，隐藏流程名和模型评分后请同事评审。

每个标题和每版文案分别标记：**可直接用 / 小改可用 / 需要重写**。标题另判是否愿意点击、是否夸大承诺；正文判断前两句、信息密度、自然语气、标题兑现、重复或虚构；配图判断是否对应本版正文、是否能据此找图/生图。不要把流量未发生前的模型分数当成实际传播效果。

记录人工评分后，再补模型评分与是否通过，专门找“模型高分但人工需重写”和“模型阻断但人工可用”的案例。优先修正具体角色的提示词、证据交接或评分标准，每次只调整能由案例解释的问题，使用同批样本复核。没有人工数据前不降低门槛或宣称多 Agent 比旧版更好。

汇总时保留分子与分母：如“可直接用 X/N 版，小改可用 Y/N 版，需要重写 Z/N 版”，并记录耗时、实际请求数和修改时间。一组 1×2 只用于冒烟验收；是否普遍改善需要更多关键词和独立样本。

这些记录可用于后续项目复盘与简历材料。流程实现、自动化测试和实际可用度分别描述；没有观测数据时不填写提升百分比。
