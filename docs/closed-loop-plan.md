# 完整运营闭环方案：创作 → 草稿 → 配图 → 发布 → 数据

> 状态：**待评审**
> 目标：把「热点创作」从"能生成"变成"能跑完一整轮运营"，并为将来打包成桌面应用做好结构准备。
> 关联文档：`docs/workbench-integration-plan.md`（能力盘点）、`docs/account-search-plan.md`（账号样本来源）

## 1. 目标与非目标

### 目标

1. **一条闭环**：搜样本 → 生成 → 存草稿 → 出配图 → 微调 → 发布 → 看数据，全在同一工具内完成，不来回导文件。
2. **每一步都可回退**：草稿可改、配图可换、发布可取消或定时；失败不丢内容。
3. **可打包**：单进程启动、数据落在用户目录、构建产物可打成安装包。

### 非目标（本期不做）

- 全自动无人值守发布（生成内容必须人工过一遍，这是硬约束）；
- 多平台（只做小红书）；
- 团队协作与权限体系；
- 云同步。

## 2. 现状与缺口

| 环节 | 已有能力 | 缺口 |
|---|---|---|
| 找样本 | 关键词搜索、账号搜索、内容库、竞品监控 | 竞品笔记还不能直接进创作 |
| 生成 | LangGraph 13 节点、评分返工、暂停接续 | — |
| 存草稿 | 草稿工坊（标题/正文/标签/素材/转发布）、内容库与竞品的批量入库 | **创作结果没有入口** |
| 配图 | 配图方案 + 结构化提示词；图片工坊已有 AI 生图接口 | **没把提示词接到生图接口** |
| 发布 | 发布中心（上传素材、Creator 发布、定时、重试） | 需要 Creator 账号；缺发布前校验 |
| 数据 | 数据洞察、竞品监控、发布记录 | 发布后的笔记数据没有回流 |
| 自动化 | 自动运营（旧简化流程） | 没复用新链路 |
| 打包 | 后端已能托管前端构建产物（`frontend_serve_static`） | 存储目录写死在代码里、没有启动器 |

## 3. 总体架构

```
┌──────────────────────────── 前端（React） ────────────────────────────┐
│ 热点创作 → 结果区（存草稿 / 生成配图）→ 草稿工坊 → 发布中心 → 数据洞察 │
└───────────────────────────────┬───────────────────────────────────────┘
                                │ REST
┌───────────────────────────────▼───────────────────────────────────────┐
│ 后端（FastAPI）                                                        │
│  creative / drafts / publish / ai(images) / files / scheduler / tasks  │
│  ├─ 任务队列：creative_analysis、ai_image_generate、publish            │
│  └─ 调度器：定时发布、自动运营                                         │
└───────────────────────────────┬───────────────────────────────────────┘
                                │
     SQLite + 本地文件（草稿素材、生成图片、报告、日志）
```

### 数据模型改动

```python
# ai_drafts 增加来源与状态
source_type: str = "manual"      # manual | creative | note | benchmark
source_task_id: int | None       # 来自哪个创作任务
source_variant_id: str | None    # 来自哪个版本（幂等键的一半）
status: str = "draft"            # draft | ready | scheduled | published
updated_at: datetime

# draft_assets 增加来源与尺寸
source: str = "upload"           # upload | generated | composed
width: int | None

# 唯一约束（幂等）

```

发布侧已有 `PublishJob.source_draft_id`、`PublishAsset.upload_status`、`external_note_id`，够用，不新增表。

## 4. 详细设计

### 4.1 创作结果 → 草稿工坊（P0）

**接口**

```
POST /api/xhs/creative/runs/{task_id}/save-to-drafts
{ "variant_ids": ["copy_0_0", "copy_0_1"],   // 为空表示该任务全部版本
  "title_prefix": "" }                        // 可选，如 "BAM摄影｜"
→ 200 { "drafts": [{"draft_id": 12, "variant_id": "copy_0_0"}], "skipped": ["copy_0_1"] }
```

**映射规则**

| 草稿字段 | 来源 |
|---|---|
| `title` | `idea.title`（可加前缀；超过 20 字截断并提示） |
| `body` | `variant.body` |
| `tags` | `variant.tags`（去 `#`、去重、最多 10 个） |
| `assets` | 该版本已有的配图（生成或上传的），没有则为空 |
| `source_type/task_id/variant_id` | 用于来源标记与幂等 |

**幂等**：同一 `(user, task_id, variant_id)` 重复保存时返回已有草稿，不重复创建；前端按钮变为「已存入草稿」。

**前端**

- 结果区每个版本卡片下方：「存入草稿工坊」「生成配图」；
- 顶部批量：「全部存入草稿」「存入选中的 N 个版本」；
- 存入后 toast 带链接跳到草稿工坊并定位到该草稿。

**验收**：5×3 结果全存 → 草稿工坊出现 15 条，标题/正文/标签与结果一致；重复点击不新增。

### 4.2 配图方案 → 内置生图（P1）

**前提**：用户已配置 `model_type="image"` 且默认的模型；否则按钮置灰并引导去「模型配置」。

**接口**

```
POST /api/xhs/creative/runs/{task_id}/generate-images   (202)
{ "variant_ids": ["copy_0_0"],
  "scope": "cover" | "all",        // 默认 cover：每版只生成第 1 张
  "size": "1024x1536",             // 3:4
  "max_images": 10 }               // 硬上限，防误触
→ { "task_id": 88, "planned": 3 }
```

**执行**

1. 校验 variant 是否存在、是否已生成过（已有时返回缓存或提示覆盖）；
2. 逐张调用 `ImageAiClient.generate_image(prompt=plan.prompt, reference_images=...)`；
3. 下载到 `storage/generated/{user}/{task}/{variant}/{n}.png`，写 `AiGeneratedAsset` + `DraftAsset(source="generated")`；
4. 并发 2、单张超时 180s、失败重试 1 次，逐张记录成功/失败，**不整体失败**；
5. 完成后通知 + 结果区显示缩略图。

**成本与安全**：运行前明确显示「将生成 N 张，约 N 次生图调用」；`max_images` 默认 10、上限 20；不自动生成全部配图，避免一次几十张。

**为什么可以直接用现有提示词**：image_plan 的 prompt 已经包含构图、镜头、光线、色彩、材质、风格、比例，并在末尾统一写了「画面中不要出现：…」，正是生图接口需要的输入。

### 4.3 草稿 → 发布中心（P0 打通，P1 增强）

**前置校验（新接口）**

```
POST /api/drafts/{draft_id}/validate
→ { "ok": false, "issues": [
     {"field": "title", "message": "标题超过 20 字"},
     {"field": "account", "message": "未绑定 Creator 账号"},
     {"field": "assets", "message": "图片未上传"} ] }
```

校验项：标题非空且 ≤20 字、正文 ≤1000 字、标签 ≤10 个且格式合法、图片 1～18 张、Creator 账号已绑定且 Cookie 有效。

**发布流程**（复用现有）

```
草稿 → POST /drafts/{id}/send-to-publish（选 Creator 账号）
     → POST /publish/jobs/{id}/assets（加素材）
     → POST /publish/assets/{id}/upload（上传到小红书）
     → POST /publish/jobs/{id}/publish（立即/定时）
     → 成功写 external_note_id，发通知
```

**增强**：发布中心详情页做成「步骤条」——账号检查 → 素材上传 → 提交 → 结果，每一步的失败原因翻译成人话（标题超长、图片格式不支持、登录失效、触发风控）。

### 4.4 发布后数据回流（P2）

- 用 `external_note_id` 通过笔记详情接口拉取互动数据（点赞/收藏/评论/浏览）；
- 存 `note_metrics`（新增轻表：note_id、采集时间、指标 JSON）；
- 数据洞察新增「我的发布」页签：按标题/时间看表现，和竞品对比。

### 4.5 自动运营 2.0（P1）

把现在的「搜索 → 改写 → 草稿」简化流程，替换为：

```
定时触发 → 跑一次热点创作（复用现有 pipeline，配置项固定）
        → 自动存草稿（每个标题选评分最高的一版）
        → 可选：自动生成封面图
        → 停在「待发布」，等人点确认（不做全自动发布）
```

保留人工确认是刻意设计：合规与账号安全都不允许无人值守发布。

### 4.6 前端信息架构调整（P1）

现在草稿/发布/图片/内容库都在「高级功能」下，闭环成立后建议重组：

| 分组 | 页面 |
|---|---|
| **创作** | 热点创作、草稿工坊 |
| **发布** | 发布中心、内容库 |
| **数据** | 数据洞察、竞品监控、关键词组 |
| **系统** | 账号绑定、模型配置、任务中心、设置 |
| **高级**（保留但弱化） | 笔记发现、数据抓取、图片工坊、视频工坊、自动运营 |

### 4.7 任务与通知

- 生图、发布都走现有 `Task` 体系（`task_type=ai_image_generate`、`publish`），任务中心可见；
- 长任务完成/失败写 `notifications`，前端顶部铃铛提示；
- 创作任务、生图任务、发布任务在草稿详情里串成一条时间线。

## 5. 打包成桌面应用

### 5.1 现状（好消息）

后端已经能在同一个端口托管前端构建产物：

```python
if settings.frontend_serve_static:
    ... SPA fallback + StaticFiles(frontend/dist)
```

即：`npm run build` 后，`python main.py` 一个进程、一个端口就能跑完整应用，不需要 Vite dev server。

### 5.2 需要先解决的三件事

| 问题 | 现状 | 方案 |
|---|---|---|
| 存储目录写死 | `storage_dir = Path("backend/app/storage")` | 改为 `settings.data_dir`，默认 `%APPDATA%/XHS_ALL_IN_ONE`，可通过环境变量覆盖 |
| 数据库路径 | 默认 `./data/spider_xhs.db` | 打包模式下默认落到数据目录 |
| 日志/报告路径 | 分散 | 统一到数据目录下的 `logs/`、`storage/` |

### 5.3 推荐路线

| 阶段 | 方案 | 说明 |
|---|---|---|
| **A** | 单进程运行 | `serve_static=true` + 构建前端；浏览器访问 `http://127.0.0.1:8000` |
| **B** | 启动器 | 小启动器（PyInstaller 生成的 exe 或 Tauri/Electron 壳）拉起后端并自动打开浏览器；带托盘图标、退出即停 |
| **C** | 安装包 | PyInstaller `--onedir` + Inno Setup/NSIS，安装到 `Program Files`，数据写 `%APPDATA%` |
| **D** | 自动更新（可选） | Tauri 壳 + 内置 sidecar，或简单地在启动时检查新版本 |

体积注意：`opencv-python`、`aiohttp`、`PyExecJS` 较大，打包后预计 150～250MB；Node 只在构建期需要，不进安装包。

### 5.4 首次启动向导

打包后应引导用户走完三步，而不是直接丢进主界面：

1. 设置本地账号密码（首次注册）；
2. 扫码绑定 PC 账号（搜索/采集）+ Creator 账号（发布）；
3. 配置文字模型（必填）和图片模型（可选，用于生图）。

## 6. 里程碑与验收

| 里程碑 | 内容 | 验收标准 | 预估 |
|---|---|---|---|
| **M1** | 创作 → 草稿 | 5×3 结果一键全存，草稿字段一致，重复保存不重复建 | 1 天 |
| **M2** | 草稿 → 发布打通 | 无 Creator 账号时明确提示；有账号时能上传素材并发布成功（测试账号） | 1 天 |
| **M3** | 生图闭环 | 选 3 个版本生成封面，图片落库、草稿可见、失败逐张提示；成本提示准确 | 2 天 |
| **M4** | 自动运营 2.0 | 定时跑一次创作 → 草稿待确认；不自动发布 | 2 天 |
| **M5** | 数据回流 | 发布后 24 小时能拉到互动数据并在「我的发布」展示 | 1 天 |
| **M6** | 打包 | 构建脚本产出一个安装包；新机器安装后能启动、建账号、配模型、跑通最小创作 | 2 天 |

总计约 **9～10 个工作日**，其中 M1+M2 是闭环的最小可用版本。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 生图费用失控 | 一次几十张图 | `max_images` 硬上限 + 运行前数量提示 + 默认只生成封面 |
| Creator 接口不稳定/风控 | 发布失败 | 步骤条展示失败原因、支持重试、不做高频自动发布 |
| 图片尺寸/格式被拒 | 发布失败 | 发布前统一转 JPG/PNG、限制 3:4 与文件大小、校验在客户端先做 |
| 打包后路径问题 | 安装版无法写文件 | 一律走 `data_dir`，禁止写程序目录 |
| 素材膨胀 | 磁盘占用 | 草稿删除时级联清理文件；提供「清理已发布草稿素材」 |

## 8. 待确认

2. **生图默认范围**：只生成封面（建议）还是全部配图？
3. **Creator 账号**：你是否已有可绑定的创作服务平台账号？没有的话 M2 只能做到「草稿待发布」。
4. **打包平台**：先做 Windows 安装包即可，还是也要 macOS？
5. **导航重组**：是否按 4.6 的方案把草稿/发布提到主流程？
