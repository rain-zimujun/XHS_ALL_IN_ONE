# 热点创作 Agent 详细职责说明

日期：2026-10-21（北京时间）

状态：M3～M12 独立模块、M13 后端串联/有限返工、M14 页面流程/阶段进度已实现；M15～M18 评审结果展示、报告和完整验收继续实施。

M14 页面默认新任务选择多 Agent，旧版综合生成收在“高级生成选项”供对照。生成任务逐阶段展示七个状态、版本、质量返工计数及模型请求预算，失败、超时、返工耗尽和停止均显示保存状态及下一步提示；历史任务没有 workflow 标记时按新的默认流程进行下一次生成，但仅查看历史不改写它。

M13.1 返工基础已完成：`revision.py` 将评审意见与旧稿作为结构化资料交回原生产者，校验只改指定 ID、其他已通过对象保持原文及绑定；提供统一请求次数/时长预算。

M13.2 已通过 `creative_workflow.py` 接入现有任务执行器：请求指定 `workflow=multi_agent` 即运行真实的十步调用链，阶段产物/评审/尝试/返工历史保存到 Task.payload.pipeline。M14 已让页面新任务默认启用该流程；历史未带 workflow 的任务继续走旧流程。

- 每个生产阶段最多两次质量返工，总调用不超过 36 次；30 分钟后不再开始新请求，每个已开始请求保持 180 秒读取超时。首次全部合格时为 10 次调用。
- 终审意见交回字段所属生产者，只改失败对象；上游变化使相关下游评审失效，受影响选题/版本重新生成并评审，保留其他稿件。
- 失败/预算耗尽/取消保存已有阶段，不输出伪合格的最终结果；重启仅标记中断，不自动重新调用模型。当前不提供跨任务自动续跑，用户手动重生成仍会新建任务并重新计费。
- 结构修复与质量返工独立计数，网络超时直接停止；只使用当前任务内部产生的可信产物链，不接受外部上传的 passed 标记作为放行依据。

范围：沿用此前 M3～M12 的开发任务安排，不重新编号、不新增一套开发任务清单。本文仅明确角色职责、输入输出、权限边界及评审交接。

项目档案：[project-change-log.md](project-change-log.md)；总路线图：[hot-content-roadmap.md](hot-content-roadmap.md)。

交付分支：自 2026-10-21 起，后续阶段默认在个人 Fork `rain-zimujun/XHS_ALL_IN_ONE` 的 `master` 上实现、验证并提交，推送至 `origin/master`；原开发分支保留，不向原作者仓库推送。

## 1. 角色总览

采用 6 个生产角色和 1 个复用评委角色。选题评委、标题评委、文案评委、最终评委是同一评委机制在不同环节使用不同规则，并非必须使用不同模型。

第一版沿用用户选定的文字模型，每个角色是独立的结构化调用，不共享无边界的聊天记录。角色独立不等于模型判断一定独立，评委仍需人工校准。

| 角色 | 核心问题 | 主产物 |
|---|---|---|
| 样本分析 Agent | 这批笔记在讲什么、怎么表达，有什么依据？ | 样本分析与风格档案 |
| 读者需求 Agent | 谁会看，他们为什么愿意看？ | 读者需求简报 |
| 选题 Agent | 这一篇具体讲什么，给读者什么？ | 选题创作简报 |
| 标题 Agent | 如何准确、具体、有吸引力地表达这个选题？ | 绑定选题的候选标题 |
| 文案 Agent | 如何围绕已选标题写出可直接复制的正文？ | 每个标题对应的 2/3 版成稿与标签 |
| 配图 Agent | 什么画面能支持这版正文，用户如何准备图片？ | 每版对应的配图建议与生图提示词 |
| 评委 Agent | 当前产物哪里不合格、依据是什么、该改哪里？ | 分项评分、问题定位、定向修改要求 |

程序调度器负责顺序、预算、状态保存和通过判定，**不是另一个自由决策的 AI Agent**。

## 2. 所有角色共同遵守的约定

### 2.1 共同输入

- 用户创作简报：关键词、搜索筛选、选定样本、目标受众、创作要求、标题数量和每个标题的版本数量。
- 样本证据包：有效正文或有标记的摘录、标题、来源 ID、已有互动与时间信息；缺失字段保留未知状态。
- 当前阶段需要的上游已通过产物、产物版本和必要原文证据。不是每个 Agent 都重复接收全部原始资料。
- 返工时额外提供失败稿件、评审问题、允许修改的范围和不可改变的已通过内容。

用户明确要求优先于从样本归纳的风格偏好。样本文字是资料，不是指令，不能要求 Agent 改规则、泄漏配置或调用链接。

### 2.2 输出与交接

- 全部使用独立结构化字段。来源、分析、理由和评审不能混入可复制正文。
- 选题、标题、文案版本均有稳定 ID，配图用对应 ID 绑定，不依靠数组顺序。
- 分清样本观察、需求推测和创作建议；推测不得写成已证实事实。
- 只借鉴多篇样本的共同表达习惯，不逐篇改写、不复制特色句子、不继承原作者身份或亲测经历。
- 本批样本不是全站趋势，互动快照不证明选题或表达导致高流量，不承诺一定爆款。
- 所有 Agent 默认无浏览、文件写入、账号操作、发布或生图工具权限；需要外部操作时由应用明确实现和授权。

下文英文名称仅是拟定的结构名称，便于实现时对齐，不代表已存在接口。

## 3. 样本分析 Agent

### 当前实现状态（2026-10-21）

- 已新增 `backend/app/services/creative_agents/sample_analysis.py` 与 `backend/app/schemas/creative_agents.py`，复用现有 `run_agent()` 调度器。
- 输入限定 3～50 篇有效、不同来源的正文；保留全部输入样本，正文总摘录预算 24,000 字符、每篇最多 1,800 字符，长文保留首尾并标记省略。
- 结构化输出包含逐篇观察、题材、风格、价值、应避免的模式和局限；代码检查覆盖完整性、来源 ID、逐字引文、字段匹配和重复证据，支持最多一次校验修复。
- 数量和引文核对不等于语义质量通过。返回元数据明确标记 `quality_review_status=not_reviewed`，类型统计来自模型分类，不能当作独立验证的事实统计。
- 提供可注入模拟模型的独立调用入口和复用现有账号归属/模型请求的传输入口；没有注册新 API、替换旧生成流程或自动发起请求。
- 输出可放入现有阶段状态并序列化；本轮未实现任务数据库检查点保存、质量评委、质量返工、页面展示或自动续跑。
- 本轮验证结果和提交状态见 [项目档案](project-change-log.md)。

### 定位

负责把“几十篇笔记”变成后续创作可以使用、又能追溯依据的资料档案；不负责直接生成标题或正文。

### 接收什么

- 本次搜索条件、有效样本及其来源 ID。
- 每篇实际送入模型的标题、正文/摘录、已有互动信息。
- 用户关键词、受众和创作要求，用于判断哪些样本特点与目标相关。

### 具体职责

1. 归纳内容类型和主题分组，例如作品展示、灵感分享、行业观察、工具体验、教程；不能把所有内容自动归为教程。
2. 提取共同表达习惯：开头方式、口语程度、句段长度、信息密度、表情使用、话题方式和结尾互动。
3. 总结样本提供的内容价值和常见切入点，指出哪些是多数样本共有、哪些只是少量个案。
4. 比较不同样本的表达特点与现有互动快照，但不宣称因果关系或真实转化率。
5. 为每条重要结论提供有效来源 ID 和必要的短摘录，标记样本差异、缺失数据和分析局限。
6. 提供可供正文 Agent 参考的代表性表达片段；片段是风格证据，不是可照抄的句子库。

### 交付什么

“样本分析与风格档案” `SampleAnalysis`：

- 分析覆盖情况及局限。
- 题材分组与来源。
- 风格特征及对应证据。
- 内容价值与常见切入点。
- 可借鉴的表达方式、应避免的模式。
- 供后续阶段引用的证据片段。

### 不允许做什么

不虚构发布时间、增长率、流量排名或读者反馈；没有读取原图时不声称分析过图片风格。统计数量由程序核对，不能凭模型印象编数字。原文被截断时说明分析基于摘录，不能声称完整阅读了全部正文。

### 评审与交接

评委检查覆盖、来源有效性、归纳是否过度，以及是否把资料指令当成任务。通过后交给读者需求和选题阶段；正文阶段也能读取风格档案与必要原文片段。

## 4. 读者需求 Agent

### 当前实现状态（2026-10-21）

- 已新增 `backend/app/services/creative_agents/reader_needs.py`，复用 M3 的结构化调度器与模型传输边界。
- 已新增 `AudienceBrief`、受众分组、共性需求和内容形式建议 Schema；用户原始受众词必须完整覆盖，输出不能添加未提供的受众词。
- 每个受众分组包含工作场景、主要使用场景、关注点、可提供的内容价值、适合形式、依据和不确定性；`sample_evidence` 只能引用 M3 已验证的 note_id，`user_requirement` 不得伪造样本来源，`hypothesis` 必须明确标记。
- 代码检查受众词覆盖、segment ID、引用 ID、证据类型和共性需求置信度；结构或依据问题最多触发一次修复。受众整理不等于市场调研，也不产生标题、正文或配图。
- 提供 `run_reader_needs()` 离线入口和 `analyze_reader_needs()` 模型传输入口；没有新增 API、页面或任务数据库写入，旧生成流程不变。
- 当前结果的 `quality_review_status` 为 `not_reviewed`，受众需求 Agent 尚未接入实际评委和完整管线。

### 定位

把宽泛的受众描述转成可用于选题的读者场景，回答“这个人为什么愿意花时间看”。

### 接收什么

用户目标受众与创作要求、已通过的样本分析，以及需要核对的样本证据。

### 具体职责

1. 将用户提供的受众按工作场景或内容需求划分，例如电商经营者、服装设计从业者、视觉制作人员、AI 创作者；不擅自推断个人敏感属性。
2. 区分不同人关注的价值：审美参考、制作思路、表达方式、行业观察或效率方法。
3. 区分样本明确体现的关注点和待验证的需求假设，为假设标注依据不足。
4. 为各类需求说明适合的内容形式与不适合的表达，例如灵感分享不必硬改成“三步教程”。
5. 给选题 Agent 提供可选的主要读者和需求，而不是要求每篇内容覆盖所有行业。

### 交付什么

“读者需求简报” `AudienceBrief`：

- 读者分组与使用场景。
- 关注点和可提供的价值。
- 支持这些判断的证据及不确定性。
- 适合的内容形式、语言倾向和应避免的表达。

### 不允许做什么

不把猜测写成已完成的市场调研；不覆盖用户明确指定的受众；不将“读者收益”统一理解为赚钱、省钱或效率提升。

### 评审与交接

评委检查与用户要求的匹配、场景是否具体、推测是否标明。通过后交给选题 Agent，由每个选题选择一个清晰的主要读者和主要价值。

## 5. 选题 Agent

### 当前实现状态（2026-10-21）

- 已新增 `backend/app/services/creative_agents/topic_selection.py`，输出 `TopicBrief`、`TopicIdea` 和 `TopicEvidence`；只生成选题创作简报，不生成最终标题、正文、标签或配图。
- 输入使用用户关键词、创作要求、1/3/5 个选题数量，以及 M3/M4 的简报。重新校验上游字段、样本 ID、受众覆盖和分组引用；不会重新发送完整采集正文或账号配置。
- 每个选题关联一个主要读者分组，包含内容类型、读者承诺、核心切入点、必须覆盖要点、依据、事实边界和差异化说明。
- 代码严格核对数量、唯一 idea ID、去除空白后的完全重复主题；每个选题至少关联两个不同的有效样本，声明来源与依据来源合集必须一致。用户要求型依据不得附带样本 ID，重复来源不能增加参考篇数。
- 提供 `run_topic_selection()` 离线入口与 `analyze_topics()` 模型传输入口；保留模型归属检查和连接 10 秒/读取 180 秒的设置。JSON、字段或引用错误最多修复一次；传输失败不自动重发，进度回调可在请求前停止。
- 当前检查的是结构和引用关系，不重新证明原文引句、依据语义、选题差异性或流量效果；M4 简报与原用户受众、批次及产物版本的绑定仍需后续管线负责。M5 单独调用仍返回 `quality_review_status=not_reviewed`；M6 已提供独立评审入口，但尚未自动串联、保存到任务数据库或接入 API/页面。
- 验证结果和提交状态见 [项目档案](project-change-log.md)。

### 定位

先确定这一篇值得写什么，再让标题 Agent 包装，避免“先写很大的标题，正文却没有内容”。

### 接收什么

用户要求、样本分析、读者需求简报，以及有效来源列表。

### 具体职责

1. 按用户要求形成 1/3/5 个不同的内容方向，不擅自减少或增加最终数量。
2. 每个方向明确主要读者、使用场景和一个核心切入点。
3. 写清楚“读者看完能得到什么”和“正文必须讲到什么”，但不直接写最终正文。
4. 在灵感分享、案例观察、观点表达、方法说明等形式中选择符合用户需求和样本的类型。
5. 为每个选题关联至少 2 个真实有效的来源，说明综合了哪些信息，而不是任意挂来源 ID。
6. 标出可使用的事实和不能承诺的内容，为后续标题和正文建立边界。
7. 检查不同选题的差异性，不用同一主题换几个词凑数量。

### 交付什么

“选题创作简报” `TopicBrief`，每项包含：

- 稳定的 `idea_id`。
- 主要读者、内容类型、核心切入点。
- 读者价值、正文应兑现的承诺。
- 必须覆盖的具体要点。
- 来源 ID、事实边界及不能使用的主张。

### 不允许做什么

不杜撰案例、数据或使用经历；不把“没有素材支持的大承诺”留给正文 Agent 自行补全；不把所有受众和关键词堆进同一篇。

### 评审与交接

选题评委检查价值、具体程度、匹配度、差异化与证据。未通过退回当前选题；通过后交给标题 Agent。

## 6. 标题 Agent

### 当前实现状态（2026-10-21，M7）

- 新增 `title_generation.py` 与 `TitleCandidates`，每个选题默认 5 个候选、支持 5～8 个；全批候选 ID 唯一，按 idea_id 绑定，标题与表达角度、读者价值、承诺、支撑要点及理由分开。
- 接收当前版本的已通过选题评审，重新核对内容指纹并程序重算分数/通过名单；旧版本、被篡改的总分或阻断问题不能只靠 `passed` 标记进入下一阶段。指纹不是签名，任务归属仍由后续管线负责。
- 默认 20 个 Unicode 字符预算，可配置 10～40；含空白标点及组合 emoji 码点，不声称等于平台长度算法。校验单行纯文本、编辑说明、全半角/大小写/空白归一后的重复以及至少三种角度标签；角度语义及承诺真实性交 M8。
- 独立离线/传输入口保留 180 秒读取超时、模型归属、一次结构修复和传输不重发。尚未接入页面或生成最终正文，候选状态为 `not_reviewed`。

### 定位

为已经确定的选题生成有吸引力、但正文能够兑现的候选标题。

### 接收什么

已通过的选题、目标读者、样本标题风格，以及用户的标题要求。

### 具体职责

1. 按既定候选数量生成不同表达角度，候选始终绑定同一个选题。
2. 优先表达具体对象、场景或可感知的价值，避免只有抽象的“高级感”“氛围感”。
3. 适度运用反差、问题、观察等表达，不把这些手法机械套在所有标题上。
4. 保持简洁自然，默认尽量控制在 20 字内；计数和平台约束由程序统一处理。
5. 标明每个候选承诺了什么、正文需要如何支撑，供评委核对。
6. 接收定向返工意见，只修正失败候选，不擅自改动已通过的选题。

### 交付什么

“候选标题集合” `TitleCandidates`：

- `idea_id`、候选 ID、标题文字。
- 表达角度、面向的读者价值。
- 标题承诺与简短创作理由，理由不混入标题。

评委进行比较并提出选择建议，程序核验后锁定每个选题的 1 个标题，最终标题数量仍为 1/3/5。

### 不允许做什么

不制造虚假的数字、效果、亲测经历或权威背书；不靠夸张标题掩盖空洞选题；不自行判定自己的标题通过。

### 评审与交接

标题评委检查吸引力、具体程度、读者收益、受众匹配、差异化和自然度，同时核对承诺能否兑现。通过后将标题及承诺一起交给文案 Agent。

> M8 标题评委已实现：`title_review.py` 复用固定六项标准，逐个候选定位问题并比较；程序从通过候选中按加权分选择每选题一个标题，同分保留候选顺序。不合格候选保留评分但不阻止同组其他合格项获选；整组无合格项时退回该选题标题组。`reviewing.py` 提供通用逐项评审校验，输出与当前候选内容/版本绑定，锁定结果在下游再次重算核验。尚未自动串联和质量返工。

## 7. 文案 Agent

### 当前实现状态（2026-10-21，M9）

- 新增 `copy_generation.py` 与 `CopyVariants`，验证当前获选标题评审后，每标题生成严格 2/3 版正文。保留 idea_id、candidate_id 和唯一 variant_id，不能改标题或偷换选题。
- body、tags、版本名称和辅助要点/来源字段独立；拦截明确编辑标签、助手开场白、占位符和末尾标签混入正文，校验重复正文、标签、数量及选题来源。
- 风格档案保留供正文参考；`covered_points` 仅为待核验的要点声明，语义覆盖、口吻自然和实质差异交 M10 及真实人工验收。
- 新增 22 项离线测试，相关回归 74 项通过；未接入真实工作流或自动返工。

### 定位

只负责写给小红书读者看的成稿，不承担配图策划和过程解释。

### 接收什么

锁定标题、对应选题与主要读者、正文必须覆盖的内容、风格档案、必要原文证据、用户要求和版本数量。

### 具体职责

1. 每个标题严格生成用户选择的 2/3 版正文，均围绕同一个标题与内容承诺。
2. 各版本在开头、叙述视角、信息组织或语言节奏上有实质区别，不只替换同义词。
3. 参考本批样本共同的句段、口吻、表情和结尾习惯；原文证据帮助保持真实风格，不照搬特色句子。
4. 优先精简、具体、有自然开头和主体；不过度总结，不机械加互动问句。
5. 默认自然分享作品、灵感或观察，用户要求教程时再写教程，不把所有内容都写成营销说明。
6. 每版单独生成相关且去重的话题标签，标签不重复塞进正文。
7. 根据评委意见只重写失败版本，保持对应标题、来源边界和已通过版本不变。

### 交付什么

“文案版本集合” `CopyVariants`，每版包含：

- `idea_id`、`variant_id`、简短版本名称。
- `body`：可直接复制的纯正文。
- `tags`：独立标签。
- 内部使用的要点/来源对应信息，放在辅助字段而非正文。

### 不允许做什么

正文不得包含“以下是为你生成的文案”、分析理由、来源编号、配图指导、正负向提示词、制作说明、免责声明、编辑备注或待填占位符。不虚构“我亲测”“客户实测”“效率提升多少”等经历与数据。

### 评审与交接

文案评委检查开头、具体信息、受众匹配、自然口吻、可直接使用程度和版本差异；检查正文是否兑现标题。通过后将锁定正文与标签交给配图 Agent，不能让配图 Agent 顺便改稿。

> M10 文案评委已实现：`copy_review.py` 按固定六项标准评每个版本，携带样本风格、锁定标题及选题边界；明确要求核对正文实际兑现情况，不能采信要点自报。所有 2/3 版都需通过再进入配图，保留失败稿件及问题，不通过不自动重评。新增 12 项离线测试，相关回归 50 项通过。

## 8. 配图 Agent

### 当前实现状态（2026-10-21，M11）

- 新增 `image_planning.py` 和 `ImagePlans`，重新验证正文评审及当前版本，每版正文独立绑定 idea_id、candidate_id 和 variant_id。
- 输出封面文字、1～6 张图片的用途/构图/比例/找图描述/正负向提示词、素材说明，禁止输出修改后的正文或标题。
- 仅调用已有文字模型进行策划，没有图片下载、生图、发布或其他工具；没有输入样本原图，提示词明确禁止宣称已经分析视觉趋势。
- 新增 11 项离线测试，与正文评委回归共 23 项通过；最终对应性、可执行性和事实素材边界交 M12，尚未接入真实用户流程。

### 定位

把每一版正文转成用户可以自己找图、排版或生图的画面方案，不生成图片文件。

### 接收什么

已通过的标题、各版正文及标签、核心内容要点，以及用户明确提供的视觉偏好和素材约束。

### 具体职责

1. 为每个 `variant_id` 设计独立且相符的画面方案，不给所有文案共用一套泛化建议。
2. 说明每张建议图片的作用，例如封面、细节展示、视觉对比或信息补充。
3. 写清主体、场景、构图、色彩、比例、文字留白和必要的画面细节。
4. 提供可用于找图的描述和可用于生图的正向/负向提示词，两者都服务于本版正文。
5. 单独提供封面文字供用户后期排版，不要求图片模型直接生成准确汉字。
6. 指出需要用户提供或核实的素材，例如真实产品细节，放在配图说明而非发布正文。
7. 接收配图评审意见，只修改画面方案，不修改标题和正文。

### 交付什么

“配图方案集合” `ImagePlans`：

- 对应的 `idea_id` 和 `variant_id`。
- 封面文字。
- 各张图片的用途与构图建议。
- 找图描述、正向提示词、负向提示词。
- 必要素材说明。

### 不允许做什么

不自动调用生图服务、不自动发布、不下载或复制原作者图片。没有分析样本原图时不得声称“热门笔记都用了这种构图”。不保证提示词能准确还原未提供的产品或服装细节。

### 评审与交接

配图评审检查与正文的对应性、提示词具体程度、可操作性和素材边界。通过后将完整标题—正文—配图组合交给最终评委。

## 9. 评委 Agent

### M12 最终评委状态（2026-10-21）

- `final_review.py` 按每个文案版本构造完整标题/正文/标签/配图组合，与原选题和样本证据对照；固定五项评分，所有版本通过才能成为最终成稿。
- 问题必须定位当前字段原句并填写责任阶段，程序按字段归属核验；选题、标题、正文和配图分别交原生产者，不允许评委直接改稿。
- 配图的对应性、可执行性及素材边界在最终评审一并检查；未新增单独配图评委调用。样本/受众仍为结构及证据校验，未独立进行模型质量评审。
- 新增 12 项离线测试；M3～M12 汇总后后端全量 563 项通过（1 条既有依赖 warning）。没有真实模型质量验收，页面和任务管线尚待 M13～M18 接入。

### 当前实现状态：M6 选题评委（2026-10-21）

- 已新增 `backend/app/services/creative_agents/topic_review.py` 实现选题评审；M8 标题、M10 正文与 M12 最终评委已完成。
- 接收用户要求、M3/M4 简报、M5 选题及正整数版本；复用上游结构/引用校验，使用输入指纹绑定关键词、要求、上游简报、选题内容、版本和评分规则，拒绝版本或指纹不匹配的评审。
- 模型只输出五项分数及理由、对应字段、来源、阻断问题/优化建议、逐字问题引句、具体修改要求和应保留内容；不允许模型输出总分、通过标记、入选名单或替换选题。
- 程序沿用既定评分表计算加权总分（保留两位小数），总分至少 6.5；读者价值、具体程度和匹配度各至少 6 分，且不能存在显式阻断问题。评分项必须齐全且唯一，布尔值、字符串、非有限值和越界分数不接受。
- 每个输入选题恰好评审一次，按 ID 还原结果顺序；通过和待修改名单由程序生成。有选题未通过时保留全部结果并返回 `revision_required`，不减少用户要求数量，`downstream_ready=false` 仅表示本批选题尚未全部通过。
- 有效的低分评审直接返回待修改，不为了通过而重评；只有 JSON、结构、引用或反馈一致性错误最多修复一次。取消回调、模型归属与连接 10 秒/读取 180 秒超时沿用现有机制，传输错误不自动重发。
- 提供 `prepare_topic_review_input()`、`run_topic_review()`、`analyze_topic_review()`；结果可序列化，调用归属既有 `topic` 阶段，不改变阶段顺序和历史状态结构。尚未实现自动选题返工（M13）、数据库保存、真实工作流拦截、API、页面或报告升级。
- 指纹用于当前内容绑定，不是数字签名或任务权限验证；实际持久化、缓存失效和下游接入仍需后续管线完成。模型评审未经过真实人工校准，不能将分数当作事实或流量保证。
- 验证结果及提交记录见 [项目档案](project-change-log.md)。

### 定位

充当阶段质检者，提出可执行的修改要求；不是另一个负责润色的写手，也不是流量预测器。

### 接收什么

当前阶段产物及版本、相关用户要求、必要上游简报和来源证据、由代码提供的固定评分规则。评委不能只看一个没有依据的最终文本，也不能以生产 Agent 的自我评价替代核对。

### 不同评审场景的职责

| 评审场景 | 必须检查 | 不通过时交还给 |
|---|---|---|
| 样本评审 | 来源有效、覆盖合理、个案与共性区分、风格结论有证据 | 样本分析 Agent |
| 受众评审 | 符合用户设定、场景具体、需求推测与事实区分 | 读者需求 Agent |
| 选题评审 | 价值、具体程度、匹配、差异化、素材能否支持 | 选题 Agent |
| 标题评审 | 简洁自然、吸引力、具体信息、承诺能兑现、候选优劣 | 标题 Agent |
| 文案评审 | 纯成稿、标题兑现、信息价值、样本口吻、版本差异 | 文案 Agent |
| 配图评审 | 对应本版正文、画面可执行、提示词具体、素材边界 | 配图 Agent |
| 最终评审 | 标题/正文/标签/封面/画面一致，来源与事实边界完整 | 提出责任阶段建议，由程序核验后定向退回 |

样本、受众的独立质量评审尚未实现，当前依靠结构及证据核验；配图质量在 M12 最终评委中检查。当前实际评委调用覆盖选题、标题、正文和最终组合。

### 每次必须交付什么

“评审结果” `ReviewResult`：

- 评审对象 ID 与产物版本。
- 每项标准的分数和可核对的简短理由。
- 问题所在的具体字段、版本或短句。
- 阻断问题、建议优化项，二者分开。
- 定向修改要求和应保留的内容。
- 标题评审的候选比较与选择建议。
- 最终评审的责任阶段建议。

例如，应指出“正文没有具体讲标题承诺的配色变化，请围绕已有样本的配色信息补充，并删除无法证明的效果表述”，而不是只写“还不够爆款，再优化一下”。

### 不能做什么

- 不直接重写标题、正文或配图，避免修改权不清晰。
- 不降低评分门槛、不删除必须评分的项目、不因为总分高就忽略阻断项。
- 不把更长、更夸张、更像营销文当作更好。
- 不把模型判断当成事实验证，不声称可证明原创或保证流量。
- 不要求输出隐藏推理过程；保存的是分项理由、证据和修改建议。

### 谁决定通过

模型负责评价，程序负责核验评分项目、计算总分、执行阻断规则和决定是否进入下一阶段。现有评分门槛保留为初始基线，后续需要人工样例校准。

同一模型担任生产者与评委可能具有共同偏差。真实验收仍由用户判断“可直接用 / 小改可用 / 需要重写”，不能用评委高分替代实际可用度。

## 10. 调度器与角色修改权

职责流转：

```text
样本分析 → 读者需求 → 选题 → 标题 → 文案 → 配图 → 最终组合
   ↓          ↓        ↓      ↓      ↓      ↓        ↓
阶段评审   阶段评审   评审   评审   评审   评审     最终评审
```

调度器负责：

1. 将正确、已通过且版本一致的输入交给下一阶段。
2. 执行结构、数量、来源 ID 和绑定关系检查。
3. 保存进度、产物、评审、调用次数与安全错误信息。
4. 根据评审定位把不合格项退给原生产者，不让 Agent 自由调用其他 Agent。
5. 执行既定返工、时间和费用约束；格式修复和内容返工都计入实际调用次数。
6. 区分质量问题与网络问题。连接 10 秒、读取 180 秒仍是单次请求设置；网络/HTTP/读取超时不自动重发。
7. 响应停止与重启，保留已完成产物；不承诺撤销已发到中转站的请求或费用。
8. 只有完整、通过评审的组合才作为最终成稿；旧流程与历史结果保持兼容。

修改权边界：

- 样本分析变更：重新核对依赖该结论的后续产物。
- 受众或选题变更：对应标题、正文与配图不得沿用旧的通过状态。
- 标题变更：重新核对对应正文是否兑现承诺、配图是否仍匹配。
- 正文变更：重新核对对应配图和最终组合。
- 配图变更：只影响该配图及最终组合，不擅自重写正文。
- 标签、数量和明显格式问题优先做确定性校验；语义修改必须交还负责角色。
- 无法在既定返工范围内解决时，保存问题并交用户处理，不无限循环。

## 11. 用户最终看到什么

主界面仍然只突出：

1. 标题选择。
2. 该标题下的 2/3 版可复制正文及各自标签。
3. 当前版本的配图建议、封面文字与生图提示词。

样本分析、受众判断、选题依据、分项评分和返工记录放在“分析与评审详情”中，默认收起，不污染复制内容。

每个阶段需有结构校验、模拟响应与失败用例；真实质量使用同一批样本、同一模型和相同要求进行新旧对比。不因完成角色拆分就宣称文案质量已经改善。
