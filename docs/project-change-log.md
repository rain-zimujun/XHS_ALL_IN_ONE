# XHS_ALL_IN_ONE 二次开发项目档案

> 这份文档用于记录本 Fork 的项目理解、产品决策、技术改动、验证结果和可复用的简历素材。
> 每完成一个小任务都要更新：日期、问题背景、实现方式、测试结果、提交号和后续边界。

## 1. 项目概览

### 1.1 原项目定位

`XHS_ALL_IN_ONE` 是一个面向小红书的全链路运营平台，原始定位覆盖：

- 小红书 PC 端与创作者平台账号登录、Cookie 管理和状态巡检。
- 关键词搜索、笔记详情、评论和用户内容采集。
- 内容库、标签、素材下载及 JSON/CSV 导出。
- AI 标题、正文、标签改写以及图片生成、图片润色和图片描述。
- 草稿编辑、发布中心、立即发布和定时发布。
- 自动运营、数据洞察、竞品监控、通知和任务中心。
- 基于 FastAPI 的 Python 后端、React 前端、SQLite/MySQL 配置和 Docker 部署。

原项目的优势是功能覆盖面广、底层小红书适配能力较完整，并且已经具备账号、任务、模型配置和发布等基础设施。它的代价是功能入口很多，采集、AI 创作和自动发布耦合在同一个运营平台中；对于只想“搜索热点 → 分析 → 写文案 → 自己配图”的使用场景，学习成本和操作路径偏长。

### 1.2 原项目技术结构

| 层级 | 原项目实现 | 本项目使用方式 |
|---|---|---|
| 小红书适配 | `apis/`、`xhs_utils/`、`static/` 签名和请求能力 | 不直接改底层 SDK，通过 `backend/app/adapters/xhs/` 调用 |
| 后端 API | FastAPI 路由、Pydantic Schema | 复用认证、账号、模型、任务和文件下载能力 |
| 业务服务 | SQLAlchemy、后台任务、调度器 | 新增热点创作和后续多 Agent 流程 |
| 前端 | React 19、Ant Design、Vite | 收敛为热点创作主流程，保留高级能力 |
| 数据持久化 | SQLite 或 MySQL | 本地试用使用 SQLite，报告和正文保存到本地存储 |
| AI 接口 | OpenAI 兼容 `/chat/completions` | 复用文字模型配置，暂不自动调用生图和发布接口 |

### 1.3 原项目分析与改造边界

原项目不是从零开始的爬虫，而是一个已经包含账号、采集、AI、发布和自动运营能力的综合平台。因此本 Fork 采取“复用基础设施、增加垂直工作流”的方式：

1. 不重复实现登录、Cookie 加密、模型配置、通用任务和文件下载。
2. 不直接修改底层签名 SDK，避免破坏原项目已有平台能力。
3. 优先完成可人工验收的热点创作流程，再实现定时日报和桌面打包。
4. 新流程默认不自动发布、不自动生图，图片由使用者自行生成或寻找有授权的素材。
5. 所有生成内容都需要人工审阅，不承诺一定爆款，也不把搜索样本当作全站趋势。

## 2. 本 Fork 的产品目标

绑定小红书 PC 账号后，用户可以：

1. 输入关键词并选择排序、时间、笔记类型和 20/30/50 篇数量。
2. 勾选需要分析的笔记，批量采集完整正文和互动数据。
3. 将本批样本交给 AI，生成多个选题、标题、可直接发布的正文、标签和配图提示词。
4. 按“标题 → 文案版本 → 配图建议”查看成套内容，复制正文或完整笔记。
5. 导出 HTML/JSON 日报，之后再复用同一流程实现自定义定时任务。

当前阶段不包含：自动发布、自动生图、绕过登录验证、保证流量、从样本图片中推断视觉趋势。

## 4. 已完成改造

### A. 热点创作基础流程

- 增加热点创作页面和主导航入口。
- 支持账号、关键词、综合/最新/点赞/收藏/评论排序、发布时间、笔记类型和 20/30/50 篇数量。

- 支持刷新后恢复历史任务、停止任务和已有正文重新分析。

### B. AI 结果与报告

- 生成 1/3/5 个标题，每个标题对应 2/3 版正文。
- 标题、正文、标签、封面文字、配图建议和生图提示词分块展示。
- 支持“复制正文”和“复制完整笔记”。
- 末尾独立话题会被分离并去重，避免正文和标签重复。
- 对模型输出进行 JSON、字段、标题数量、版本数量、重复正文、引用来源和编辑说明校验。
- 生成 HTML 阅读版和 JSON 完整数据，保存完整采集正文。

### C. 可靠性与安全

- 创作分析使用连接超时 10 秒、读取超时 180 秒。
- 网络或模型读取超时不自动重试，避免中转服务已经完成请求时重复计费。
- 采集正文在后台逐条保存，部分笔记失败不会丢失成功结果。
- 历史结果兼容旧结构，不伪造不存在的文案版本，不修改数据库原始正文。
- 报告文本 HTML 转义，报告下载执行用户归属校验。
- 账号、模型和任务均执行用户所有权校验。

### D. 界面收敛

- 主导航突出“热点创作、账号绑定、模型配置”。
- 原项目其他页面保留在“高级功能”中，默认折叠而不是删除。
- 图片模型、高级登录方式和其他专业设置默认折叠。
- 新任务默认受众：`电商、服装行业、AI、时尚行业、营销行业、美工、后期从业者`。

## 5. 当前多 Agent 改造

### 5.1 已确认的阶段拆分

目标流程为：

`样本分析 Agent → 读者需求 Agent → 选题 Agent → 选题评委 → 标题 Agent → 标题评委 → 文案 Agent → 文案评委 → 配图 Agent → 最终评委`

每个阶段有独立输入、结构化输出、评审意见和最多 1～2 次返工。网络超时不属于内容返工，不会由 Agent 调度器重复发送。

### 5.2 M0～M2 基础层

本轮新增但尚未接入旧生成流程的基础模块：

- `creative_quality.py`：固定的选题、标题、正文和最终组合评分标准，包含权重、阻断项、总分和通过条件。
- `creative_pipeline.py`：可序列化的阶段状态、尝试记录、当前阶段、阶段输出和评审结果；尚未接入数据库持久化。
- `creative_orchestrator.py`：统一处理结构化 JSON 解析、Pydantic 字段校验、阶段进度回调和内容校验失败返工。
- `test_creative_agents.py`：覆盖评分、阶段状态、JSON 修复、耗尽重试和传输错误不重试。

本轮的设计原则是：先搭建稳定的 Agent 基础层，再逐步替换原来的单次综合分析；基础层完成不会改变当前用户可见的旧流程。

### 5.3 评委标准

标题评委关注：点击吸引力、具体程度、读者收益、关键词和受众匹配、差异化、自然度。

文案评委关注：前两句吸引力、具体信息、目标读者匹配、小红书语气、收藏/转发价值、直接发布可用度。

最终评委关注：标题和正文一致性、正文是否兑现标题、配图是否匹配、标签是否重复、事实和素材边界。

任何阻断项不通过时，结果不能直接进入最终展示；评委只能提出返工建议，不能降低代码内置的通过阈值。

## 6. 质量问题与后续优化

最近真实结果的问题不是 JSON 格式，而是内容策略：标题容易停留在“颜色/氛围/设计描述”，正文容易变成作品说明，缺少明确读者收益。下一阶段不继续堆长提示词，而是分阶段生成并评审：

1. 先让样本分析 Agent 提炼高频选题、开头结构、内容价值和受众痛点。
2. 让选题 Agent 先写清楚“读者为什么要看”和“这篇提供什么”。
3. 标题 Agent 先生成 5～8 个候选，再由标题评委挑选 2～3 个。
4. 文案 Agent 只负责围绕已通过的标题写可直接发布正文。
5. 配图 Agent 不再干扰正文写作，只处理画面方案和提示词。
6. 最终评委检查标题、正文、标签和配图是否成套。
