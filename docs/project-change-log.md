### 2026-10-28 选题返工使用目标稿件的紧凑上下文

- 背景：为避免选题质量返工重新发送完整样本分析和受众简报，新增返工上下文投影后，回归测试发现目标选题列表为空。原始选题 Agent 输入是上游生产上下文，不包含已经生成的 `topic_brief`。
- 修复：返工目标选题现在从保存的 `previous_output.ideas` 中按 `target_ids` 提取；提示仅携带目标选题、该选题原有获批 claim、字段级 `revision_briefs` 及用户要求，减少完整上游内容重复传输。返工接收逻辑仍恢复所有非目标选题原稿，所以已经通过评分的选题不需要改变。
- 自审与验证：选题紧凑上下文、选题生成/来源、目标字段进展、非目标原稿恢复及质量返工接续专项 **73 项通过**；`git diff --check` 通过。真实模型运行未在本次离线测试中执行。
- 边界：紧凑上下文降低输入规模，不保证模型遵守修改指令；目标选题仍需完整重新评审，质量门槛与两轮返工上限不变。下一步从隔离任务 #124 的失败快照接续真实 Qwen 7B 验证。

### 2026-10-28 选题返工重试反馈具体到未改字段

- 背景：真实 Qwen 接续任务 #125 确认上下文压缩后仍原样返回 `reader_promise`、`must_cover` 和 `evidence`。失败评审意见同时要求“补出具体步骤/案例”，但当前获批结论只支持提示词、流程/技巧，并不足以支撑实际案例承诺；泛化提示没有将此冲突解释给重试调用。
- 实现：仅当选题返工因指定字段完全未变化而进入格式/交接重试时，追加未变化字段清单、每字段修正方向及该目标选题对应的获批短结论；明确证据不足就收窄 topic/承诺/覆盖点，不得捏造步骤、案例或效果。已通过选题仍由程序原样恢复，不参与这次修改。
- 自审与验证：选题返工紧凑上下文、二次修正提示、选题来源/进展/恢复专项 **73 项通过**；`git diff --check` 通过。真实 Qwen 接续验证继续进行。
- 边界：这是同一次 producer 调用内的格式/交接重试，不重置累计请求数、质量返工轮次或内容评审标准；若仍无进展则按原失败快照规则停止。

### 2026-10-28 选题返工提供精简受众分组摘要

- 背景：真实任务 #126 按上一轮提示收窄了读者承诺、覆盖点和证据，但评委随后指出应改为更匹配的主要受众。选题返工请求只带了合法 `segment_id` 列表，没有各组的受众词和场景，因此无法合理选择其他分组。
- 实现：返工提示沿用 M4 精简后的受众摘要（受众词、角色场景、主要场景、关注点、内容价值和限制），不带回完整样本正文或 M3 分析。已通过选题仍不进入目标列表，接收时继续按保存稿逐字恢复。
- 自审与验证：选题上下文、反馈和非目标恢复专项 **73 项通过**。真实任务 #126 的首轮目标选题在网络重试后已按证据收窄；后续评委反馈暴露受众信息缺失，当前补充待下一次真实 Qwen 接续验证。
- 边界：受众摘要仅帮助在已有 segment 中选择，不放宽用户受众覆盖、来源和质量评分要求；最终选题仍需评委通过。

### 2026-10-28 选题返工明确主要受众字段的修正动作

- 背景：真实 Qwen 接续任务 #127 已按证据收窄 `reader_promise`、`must_cover` 和来源；无进展错误缩小到 `primary_segment_id`。返工提示虽然有受众摘要，但没有告诉模型按该字段必须更换到哪个判断依据。
- 实现：针对 `primary_segment_id` 添加按受众词、主要场景和内容价值选择合法分组的重试指导；不由程序猜测或强制替换 ID，仍由模型结合目标选题语义选择，最后继续执行原受众匹配评审。
- 验证：专项测试检查第二次交接反馈包含“必须更换”操作指引；选题返工/来源/接续专项待运行后记录。真实 Qwen 继续从 #127 的 topic 快照接续。
- 边界：程序不把评分通过的选题加入 `target_ids`，也不改其内容；未通过目标仍需评委复核，来源和评分门槛不变。

- 调整：每个未通过目标选题必须至少实质修改一项被评委点名、可由生产者控制的字段；只要未通过目标整体原样返回仍拒绝。通过本地进展检查后，目标项立刻重新进入完整评审，由评委按原门槛决定是否通过；证据、来源、Schema 和受众关联校验不变。
- 保留：已通过选题不进入 `target_ids`，不要求改动，并由程序逐字恢复保存稿。质量返工轮数和请求预算不变。
- 验证：选题进展、上下文、接续专项更新中；真实 Qwen 后续从 #128 接续，观察收窄后的选题是否能得到评委通过。

### 2026-10-28 选题返工补充最少来源结构提示

### 2026-10-28 选题质量返工只要求未通过目标项有进展

- 背景：真实 Qwen 任务 #120 的两轮选题质量返工中，生产 Agent 连续原样返回，评委指出的目标选题问题没有修正。用户补充确认，已经评分通过的选题不应被要求为了返工而修改。
- 实现：`target_ids` 内每个未通过选题至少要修改一个实质内容字段；模型即使在完整输出中改动其他已通过选题，接收节点也会按保存稿逐字恢复非目标项。质量评审意见仍只要求解决目标项的问题，不降低目标项评审门槛或返工次数上限。
- 自审与验证：新增测试覆盖目标内容完全不变时拒绝、有实质变化时通过，以及目标项返工时已通过非目标选题被逐字恢复。选题、条件返工与接续专项 **106 项通过**；Python 编译和 `git diff --check` 通过，1 条既有 LangGraph 弃用 warning。真实模型接续尚未执行。
- 边界：进展检测不等于评分保证；目标选题仍需重新经过选题评委。当前真实模型验证将从新的隔离接续任务继续，原任务 #120 不改写。

### 2026-10-28 Qwen 真实验证恢复受众漏词后的安全接续

### 2026-10-28 选题来源集合由证据确定性绑定

- 背景：真实接续任务 #122 的 Qwen 选题第二次输出中，`source_note_ids` 包含了本选题 evidence 没有引用的两个样本，触发来源合集不一致；该字段本质上是 evidence 来源的派生索引。
- 实现：选题 TypedDict 不再要求模型返回程序所有的 `idea_id` 和派生字段 `source_note_ids`；首次生成按顺序分配稳定 ID，返工按保存稿顺序重新绑定 ID。接收适配器再按每个 idea 的非 `user_requirement` evidence.note_ids 重建来源集合；随后仍执行至少两个来源、合法 claim/note 配对及其余业务校验。
- 自审与验证：新增来源集合派生测试，并保留未知来源、来源不足、证据重复和 claim 错配的拒绝测试。真实任务 #122 将从失败处继续验证；不跳过证据业务校验。
- 边界：如果 evidence 本身只覆盖一个样本，程序不会补造第二个来源，仍会失败并要求模型提供充分的获批证据。
- 接续：恢复白名单允许最近两次均为已知 topic 来源绑定错误（claim/note 错配或派生来源集合不一致）的失败从 topic 节点重试；恢复后仍完整执行所有本地校验。

### 2026-10-28 Qwen 选题质量返工按问题字段拆解

### 2026-10-28 选题评审问题引用由程序绑定字段原文

### 2026-10-28 选题引用去重与真实状态复核

- 背景：真实 Qwen 接续任务 #118 的 topic 输出在 `evidence.note_ids` 内重复引用同一 note，两个重试均未自行修正；相关 ID 均在合法集合内，且重复项并不增加证据覆盖。

- 边界：去重只消除重复元素；去重后仍需满足至少两个不同样本来源及 evidence/source 集合一致，不满足则照常拒绝。

### 2026-10-28 受众覆盖不足失败的保守接续

- 背景：真实 Qwen 任务 #117 的 audience 分组在两次调用后仍遗漏 3 个用户受众词；缓存中已有 2 个结构、来源均通过校验的分组。旧恢复策略不允许接续此类业务失败，造成样本阶段成果无法复用。
- 实现：只对连续两次“缺少受众词且没有其他分组/来源错误”的失败开放接续；程序将遗漏词填入已有分组的容量，不创建无证据的新分组。结果限制披露这是技术性补齐、需人工复核。来源错误、Schema 错误及其他交接失败仍不可借此绕过。
- 自审与验证：新增恢复精确节点、上游阶段不重复、人工复核披露及其他错误拒绝测试；受众与恢复专项 **58 项通过**。真实任务 #117 待代码生效后继续运行。
- 边界：本地补齐只保证用户输入受众词完整出现，不宣称这些人群属于同一使用场景或有样本支持；已有分组容量不足时仍会失败。

### 2026-10-28 选题重复来源错误的精确接续

- 背景：任务 #118 在 audience 通过后进入 topic，Qwen 两次输出重复的 `evidence.note_ids`，落入“同一条 evidence.note_ids 不可重复”失败。前序 audience 已保存，预算剩余充足。
- 实现：恢复白名单仅接纳连续两次完全相同的重复来源错误（note、claim 或 source_note_ids）；Schema 增加唯一项声明，响应程序稳定去重后仍完整执行现有来源绑定、至少两个不同来源和集合一致校验。
- 自审与验证：精确错误允许接续、非精确/混合错误拒绝、Topic Schema 与重复来源适配器 **4 项通过**。待运行代码载入后从 #118 的 topic 节点接续。

### 2026-10-28 受众证据来源由程序绑定

- 背景：恢复三路样本分析后的真实 Qwen 运行已完成 7 个样本批次和 7 个样本证据评审批次；读者需求阶段反复将获批 `claim_id` 与来自其他 claim 的 `note_id` 错配。两次结构化重试仍返回错配组合，说明让模型同时组合两个 ID 集合不稳定。

## 1. 项目概览

### 1.1 原项目定位

`XHS_ALL_IN_ONE` 是一个面向小红书的全链路运营平台，原始定位覆盖：

- 小红书 PC 端与创作者平台账号登录、Cookie 管理和状态巡检。
- 关键词搜索、笔记详情、评论和用户内容采集。
- 内容库、标签、素材下载及 JSON/CSV 导出。
- AI 标题、正文、标签改写以及图片生成、图片润色和图片描述。
- 草稿编辑、发布中心、立即发布和定时发布。
- 自动运营、数据洞察、竞品监控、通知和任务中心。
- 基于 FastAPI 的 Python 后端、React 前端、SQLite/MySQL 配置和 Docker 部署。

原项目的优势是功能覆盖面广、底层小红书适配能力较完整，并且已经具备账号、任务、模型配置和发布等基础设施。它的代价是功能入口很多，采集、AI 创作和自动发布耦合在同一个运营平台中；对于只想“搜索热点 → 分析 → 写文案 → 自己配图”的使用场景，学习成本和操作路径偏长。

### 1.2 原项目技术结构

| 层级 | 原项目实现 | 本项目使用方式 |
|---|---|---|
| 小红书适配 | `apis/`、`xhs_utils/`、`static/` 签名和请求能力 | 不直接改底层 SDK，通过 `backend/app/adapters/xhs/` 调用 |
| 后端 API | FastAPI 路由、Pydantic Schema | 复用认证、账号、模型、任务和文件下载能力 |

| 前端 | React 19、Ant Design、Vite | 收敛为热点创作主流程，保留高级能力 |
| 数据持久化 | SQLite 或 MySQL | 本地试用使用 SQLite，报告和正文保存到本地存储 |
| AI 接口 | OpenAI 兼容 `/chat/completions` | 复用文字模型配置，暂不自动调用生图和发布接口 |

### 1.3 原项目分析与改造边界

原项目不是从零开始的爬虫，而是一个已经包含账号、采集、AI、发布和自动运营能力的综合平台。因此本 Fork 采取“复用基础设施、增加垂直工作流”的方式：

1. 不重复实现登录、Cookie 加密、模型配置、通用任务和文件下载。
2. 不直接修改底层签名 SDK，避免破坏原项目已有平台能力。
3. 优先完成可人工验收的热点创作流程，再实现定时日报和桌面打包。
4. 新流程默认不自动发布、不自动生图，图片由使用者自行生成或寻找有授权的素材。
5. 所有生成内容都需要人工审阅，不承诺一定爆款，也不把搜索样本当作全站趋势。

## 2. 本 Fork 的产品目标

绑定小红书 PC 账号后，用户可以：

1. 输入关键词并选择排序、时间、笔记类型和 20/30/50 篇数量。
2. 勾选需要分析的笔记，批量采集完整正文和互动数据。
3. 将本批样本交给 AI，生成多个选题、标题、可直接发布的正文、标签和配图提示词。
4. 按“标题 → 文案版本 → 配图建议”查看成套内容，复制正文或完整笔记。
5. 导出 HTML/JSON 日报，之后再复用同一流程实现自定义定时任务。

当前阶段不包含：自动发布、自动生图、绕过登录验证、保证流量、从样本图片中推断视觉趋势。

### C. 可靠性与安全

### 5.5 M3 样本分析 Agent（独立模块）

问题背景：原综合提示词同时承担样本归纳、选题、标题、正文和配图，难以单独核对样本分析是否正确。M3 先拆出可测试的分析模块，不改变用户正在使用的旧流程。

技术实现：

- 新增 `backend/app/schemas/creative_agents.py`：逐篇观察、原文证据、题材/风格/价值模式和分析局限的 Pydantic 模型；未知字段不接受，分析结果不包含发布正文。
- 新增 `backend/app/services/creative_agents/sample_analysis.py`：独立样本分析提示词、白名单输入、来源覆盖/引文校验、程序计算的证据篇数与版本元数据。
- 支持 3～50 篇有效样本，不静默丢弃重复或空正文；对非法输入明确报错。总正文摘录预算 24,000 字符，每篇最多 1,800 字符，保留首尾并记录截断；标题最多 160 字符，额外标题字段也记录截断。
- 缺失或非法互动数据保留为未知，不当作观测到的零；不发送账号 ID、Cookie、API Key、原始响应、作者信息或媒体地址等非必要字段。
- 扩展 `creative_orchestrator.py` 的可选 `validate_output` 回调，使覆盖和来源错误可进入既有最多一次修复流程；补齐畸形 Markdown 代码块的可控失败，并避免将校验输入值/未知字段名抄入错误记录。
- 模型传输入口复用现有模型归属检查、连接 10 秒/读取 180 秒的超时分类；网络、HTTP 或响应解析失败不自动重发。
- 新增 `tests/backend/test_creative_sample_agent.py`，使用模拟响应和内存测试数据库，不调用真实账号或付费模型。

### 5.8 M6 选题评委 Agent（独立模块）

问题背景：M5 的结构和来源 ID 校验不能判断一个选题是否具体、有价值或受到样本支持。M6 将生产与评价分离，让评委给出分项判断和定位明确的反馈，再由程序计算通过结果，避免模型自行修改规则或用一句“还不够爆款”要求无目的返工。

技术实现：

- 扩展 `backend/app/schemas/creative_agents.py`：新增 `TopicCriterionScore`、`TopicReviewIssue`、`TopicJudgement`、`TopicReviewResponse`；评委只交付分数、依据、问题和修改要求，模型输出不得夹带总分、通过标记或重写的选题。
- 新增 `backend/app/services/creative_agents/topic_review.py`：校验全部选题覆盖、五项评分唯一性、来源/关联选题 ID、问题字段与逐字引句；低于分项参考线必须有对应修改意见，阻断项低分必须明确标为阻断。
- 复用既定 `TOPIC_RUBRIC`：读者价值 30%、具体程度 25%、匹配度 20%、差异化 15%、样本依据 10%。加权总分保留两位小数，至少 6.5；前三个阻断项各至少 6 分，并且不能存在显式阻断问题。仅将原有 6.5 提取为共享常量 `REVIEW_PASS_THRESHOLD`，未调整评分权重或门槛。
- 上游 M3～M5 产物重新执行结构及引用校验；以正整数 `topic_revision` 和 SHA-256 输入指纹绑定用户要求、上游内容、选题和评分规则。模型不得返回其他版本的评审，字典键顺序不影响指纹。
- 程序生成 `TopicReviewResult`：保留所有选题的评审、通过名单和待修改名单，按原选题顺序输出；不静默删除低分选题，不减少用户要求的 1/3/5 个数量。未全部通过时返回 `revision_required` 与 `downstream_ready=false`。
- 有效的低分或显式阻断结果是正常完成的评审，不自动重评或改稿；JSON、结构、引用和反馈一致性错误仍最多修复一次。网络/HTTP/读取超时不重发，模型归属和三分钟读取超时沿用现有传输层。
- 新增 `tests/backend/test_creative_topic_review.py`：84 项离线用例，覆盖数量、指纹/版本、上游输入、规则计算、阻断优先、通过/待修改名单、反馈定位、伪造评分字段、非法数值、有限修复、取消、跨用户权限和安全传输错误。

接口与兼容性：提供 `prepare_topic_review_input()`、`run_topic_review()` 和 `analyze_topic_review()` 内部入口；模型评语与程序判定分开保存，结果可序列化。评委归属既有 `topic` 阶段，不修改 `PIPELINE_STAGE_ORDER`；未增加 API、页面、任务数据库写入、报告结构或自动选题返工。M5 仍可独立运行且返回未评审状态，M6 尚未自动串入旧流程；原计划 M13 的质量返工仍待实现。

校验边界：指纹只用于内容绑定，不是签名或权限凭证；后续管线仍需核对任务归属、当前版本和缓存失效。逐字引句只核对待评审选题中的位置，不重新核实原始全文或图片；模型评分和理由仍可能有偏差，需要人工校准，不能据此宣称真实文案可用率或流量提升。
